# dev 프로젝트 매칭 리허설 실행 방법

dev DB를 초기화한 뒤 `/test/seed/...` API로 QA 계정과 프로젝트 출발선을 만들고, 매칭 차수를 단계별로 넘기며 리허설하는 방법이다. 프론트 QA가 지원, PM 결정, 자동 선발, 발표 화면을 실제 규모의 데이터로 확인할 때 쓴다.

계정, 비밀번호, dev Basic Auth 정보는 노션의 QA 계정 문서에 있다. 이 레포는 공개 레포라 이 문서에는 계정을 적지 않는다.

## 사전 조건

- 모든 API는 `/test/seed/...` 아래에 있고 dev ingress의 Basic Auth를 거친다. Swagger에서 출발선은 `Test | 시딩`, 차수 요약·봇·넘기기는 `Test | 매칭 리허설` 태그에 있다.
- 시딩 API는 `app.seed.enabled=true`이고 `prod` 프로필이 아닌 서버에만 있다.
- QA 계정 이메일 도메인은 `university.neordinary.com`으로 고정이다. `app.seed.email-domain` 설정은 다른 더미 시딩에만 쓴다.

## 데이터 층

| 층 | 만드는 API | 지우는 시점 |
|---|---|---|
| 골격(기수, 학교, 지부, 약관, 11기 커리큘럼) | 앱 기동 시 Flyway | DB 초기화 때만 |
| 기본 데이터(계정, 챌린저, 운영진 역할, 학습·출석·공지·상벌점·채팅, 매칭 지부 이동 4명) | `POST /test/seed/qa` | DB 초기화 때만 |
| 프로젝트(프로젝트, 지원 폼, 지원서, 팀원, 매칭 차수) | `POST /test/seed/projects/starting-line` | 리허설마다 `DELETE /test/seed/projects` |

## DB 초기화 직후 한 번

Flyway는 골격만 넣고 QA 계정은 만들지 않는다. dev처럼 `APP_SEED_QA_AUTO_RUN=true`(`app.seed.qa-auto-run`)를 켠 환경에서는 앱이 뜬 뒤 QA 시딩 전체가 백그라운드에서 한 번 돈다. 처음에는 계정 비밀번호 해시 때문에 수십 초 걸리고, 결과는 `QA 시딩 자동 실행` 로그로 남는다. 이미 있으면 건너뛰므로 재시작마다 돌아도 결과가 같다. 이 설정을 켜지 않은 환경에서는 아래 API를 직접 부른다.

1. `POST /test/seed/qa`를 부른다. 본문은 없다.

응답의 `steps`는 계정, 학습, 출석, 공지, 상벌점, 채팅, 매칭 지부 이동 순서로 단계별 결과를 담는다. 단계마다 따로 저장하므로 한 단계가 실패해도 앞 단계는 남는다. 계정 단계가 `FAILED`이면 뒤 단계는 `NOT_RUN`이다. 다시 부르면 이미 있는 것은 건너뛰고 `UNCHANGED`를 돌려준다. 한 단계만 다시 하려면 `POST /test/seed/qa/{step}`을 부른다. `step`은 `accounts`, `learning`, `attendance`, `notices`, `points`, `chat`, `project-transfers` 중 하나다.

리허설 중 지부 이동을 해제했으면 `POST /test/seed/qa/project-transfers`로 되돌린다.

## 리허설 준비

1. `DELETE /test/seed/projects`를 부른다. 본문은 생략할 수 있다. 본문이 없거나 `gisuId`가 `null`이면 활성 기수가 대상이다. 그 기수의 프로젝트, 지원 폼, 지원서, 팀원, 매칭 차수를 지우고, 지운 차수의 자동 선발·발표 알람도 취소한다. 계정과 지부 이동 기록은 지우지 않는다.
2. `POST /test/seed/projects/starting-line`을 부른다. 본문은 없다. 11기 다섯 지부의 출발선을 만든다. QA 계정이 없으면 400 `SEED-0101`이다. 응답의 `failed`가 0이 아니면 다시 부른다. PO마다 남은 단계부터 이어서 실행한다.
3. 운영진 계정으로 지부의 QA 프로젝트 2개에 TO를 넣고 공개한다. 승인 대기 프로젝트는 TO 관리 화면에 나오지 않으므로 프로젝트 화면에서 넣는다.
4. 운영진 화면에서 매칭 차수(1·2·3차와 랜덤 매칭)를 등록한다. 시각은 미래로 등록한다. 응답에서 차수 ID를 확인한다.

출발선을 다시 만들어도 지부별 모양은 같다. 프로젝트 ID는 바뀌지만, 봇의 무작위 키가 차수·프로젝트 ID가 아니라 지부, 유형, 차수 번호, PO 계정이라 리허설마다 같은 그림이 나온다.

## 1·2·3차 진행 순서

차수 ID가 `{id}`일 때 다음 순서로 부른다. 넘기기 요청 본문은 `{"step": "<단계>"}`다.

1. `POST /test/seed/matching/rounds/{id}/advance`에 `APPLICATION_START`를 보낸다. 지원 시작이 지금이 되고 바로 지원할 수 있다.
2. `POST /test/seed/matching/rounds/{id}/bot-applications`를 부른다.
3. QA가 A·B 계정으로 직접 지원한다.
4. `GET /test/seed/matching/rounds/{id}/summary`로 요약을 확인한다.
5. `advance`에 `APPLICATION_CLOSE`를 보낸다. 지원 마감이 지금이 되고 PM 결정 기간이 시작된다.
6. QA가 PM 계정으로 QA 프로젝트의 지원자를 결정한다.
7. `POST /test/seed/matching/rounds/{id}/bot-decisions`를 부른다.
8. `advance`에 `DECISION_DEADLINE`을 보낸다. 선발 마감이 지금이 된다.
9. 약 1분 기다린 뒤 요약의 `round.autoDecided`가 `true`인지 확인한다. 서버의 실제 스케줄러가 선발 마감 1분 뒤(`deadline-buffer-minutes` 기본 1) 자동 선발을 실행한다. 넘기기는 자동 선발을 직접 실행하지 않는다.
10. `advance`에 `RESULT_PUBLISH`를 보낸다. 발표 시각이 지금이 되고, 스케줄러가 바로 결과를 공개한다. 요약의 `round.published`가 `true`가 되면 지원자·PM 화면과 요약을 비교한다.
11. 다음 차수로 넘어가 1번부터 반복한다. 앞 차수가 발표되기 전에 다음 차수를 시작하면 409 `SEED-0301`이다.

9번에서 1분이 지나기 전에 `RESULT_PUBLISH`를 보내면 409 `SEED-0302`다. 기다렸다가 다시 보낸다.

## 랜덤 매칭 차수 진행 순서

3차를 발표하면 서버가 약 1분 뒤 랜덤 배정을 자동으로 실행한다. 그 뒤 랜덤 차수를 다음 순서로 넘긴다.

1. `advance`에 `ADJUSTMENT_START`를 보낸다. 조정 기간에는 운영진이 수동 배정·해제를 한다.
2. `advance`에 `ADJUSTMENT_END`를 보낸다.
3. `advance`에 `FINAL_PUBLISH`를 보낸다. 랜덤 결과가 공개된다.

랜덤 배정 전에 조정 단계로 넘기면 409 `SEED-0304`다. C 계정과 남은 사람이 어느 팀에 배정됐는지 이 단계에서 확인한다.

## API별 동작

| API | 하는 일 |
|---|---|
| `POST /test/seed/projects/starting-line` | 지부마다 명단 순서상 마지막 PLAN 2명은 프로젝트 없이 둔다. 첫 PLAN 2명은 QA 프로젝트로 제출만 해 승인 대기·TO 비움으로 둔다. 나머지 PLAN은 PO가 제출하고 `superadmin`이 TO를 넣어 공개한다. 개발 파트는 Web PE와 Mobile PE 중 하나만 쓴다. |
| `GET .../summary` | 차수 하나의 지금 상태를 DB에서 직접 센다. 운영 화면(TO 관리, 매칭 현황, PM 지원자 목록) 숫자가 맞는지 판단하는 기준값이다. 화면과 요약이 다르면 프론트나 운영 API 쪽 버그다. |
| `POST .../bot-applications` | 차수 지부를 매칭 지부로 가진, 차수 유형 파트의 팀 없는 사람 중 `applyRate`(기본 0.8)만큼이 한 곳씩 지원한다. TO가 남은 공개 프로젝트 중 인기도에 비례해 고르고, 직전 차수에 떨어진 프로젝트는 고르지 않는다. 주관식 답변은 `[봇]`으로 시작한다. 다시 부르면 지원자가 늘지 않는다. |
| `POST .../bot-decisions` | 프로젝트·파트마다 목표 = max(올림(`fillRate` × 지터 × TO) − 이미 채운 인원, 최소 선발 인원)만큼 합격시키고, 남은 지원자의 절반은 불합격, 절반은 미결정으로 둔다. `fillRate` 기본은 1차 0.6, 2차 0.85, 3차 1.0이다. 이미 결정된 지원서는 건드리지 않는다. 결정자는 프로젝트 PO다. |
| `POST .../advance` | 차수 시각을 테스트 전용 SQL로 한 단계 당기고, 같은 지부·유형 차수의 알람을 새 시각으로 다시 맞춘다. 응답에 바뀐 시각(`timeChanges`), 다시 맞춘 알람 시각(`timers`), 차수 요약(`summary`)이 들어 있다. |

봇 API와 넘기기 API는 실행 뒤의 차수 요약을 응답에 함께 돌려준다. 봇 요청 본문은 생략할 수 있고, `seed`, `excludeMemberIds`, `excludeProjectIds`로 결과를 바꿀 수 있다.

## QA 몫 규칙

- QA 프로젝트는 지부마다 2개다. 출발선에서 승인 대기로 시작한 프로젝트로, 명단 순서상 첫 두 PM의 프로젝트다. 봇은 QA 프로젝트에 지원하지만 결정하지 않는다. 결정은 QA가 PM 계정으로 한다.
- 프로젝트 없는 PLAN 2명은 운영진 직접 등록과 PM 제출 뒤 운영진 공개 두 경로를 시험하는 몫이다.
- 출발선 TO는 지부 매칭 인원 중 n/(n+4)만 시딩 프로젝트 n개에 나눈다. 나머지는 QA 프로젝트 2개와 직접 등록 2개에 QA가 넣을 몫이다.
- A·B·C 계정은 지부마다 매칭 파트(디자인, Web PE, Mobile PE)별로 명단 순서상 첫 일반 챌린저 3명이다. 지부 안 학교는 가나다순으로 놓는다. 지부 이동 4명은 빠진다. 지부당 9명이고, 봇은 이 계정으로 지원하지 않는다. 어느 계정이 A·B·C인지는 요약의 `qaReserved`에 나온다.
- 자동 선발이 PM의 불합격을 뒤집는 흐름은 QA 프로젝트에서 확인한다. PM 계정으로 지원자를 모두 불합격시킨 뒤 선발 마감으로 넘기면, 자동 선발이 불합격자 중에서 최소 선발 인원만큼 합격시킨다. PM 결정 자체에는 최소 선발 인원 검사가 없다.

## 넘기기 시각 규칙

- 넘긴 단계의 시각은 지금이 된다.
- 아직 오지 않은 단계와 같은 지부·유형 뒤 차수의 시각 중 내일 같은 시각보다 이른 것은 내일 이후 한 시간 간격으로 민다. 그보다 늦게 등록한 시각은 그대로 둔다. 그래서 QA가 넘기기 전에는 차수가 저절로 진행되지 않는다.
- `RESULT_PUBLISH`로 넘길 때는 선발 마감을 5분 이상 앞으로 당긴다. 발표는 선발 마감보다 5분 이상 뒤여야 하기 때문이다.
- 이미 지난 단계를 다시 보내면 시각은 그대로 두고 알람만 다시 맞춘다(`outcome`이 `ALREADY_REACHED`). 알람이 꼬였을 때 이것으로 복구한다.
- 알람은 서버 메모리에만 있다. 리허설 중 서버가 재시작하면 DB 시각 기준으로 다시 등록되므로, 내일로 밀어 둔 시각이 지나면 그때 저절로 진행될 수 있다.
- 넘기기는 같은 지부의 다른 유형 차수와 기간이 겹치는지 검사하지 않는다. 운영진 화면의 차수 등록은 유형과 상관없이 지부 안에서 기간이 겹치지 않게 막지만, 넘기기로 디자인 차수를 밀면 개발 차수와 기간이 겹칠 수 있다. 그래서 한 지부에서는 디자인과 개발 중 한 유형을 랜덤 매칭 발표까지 마친 뒤 다른 유형을 시작한다.

## 거부와 에러 코드

| 코드 | 상태 | API | 뜻 |
|---|---|---|---|
| `SEED-0101` | 400 | 출발선 | QA 계정이 없다. `POST /test/seed/qa`를 먼저 부른다. |
| `SEED-0301` | 409 | 넘기기 | 앞 차수 결과가 아직 발표되지 않았다. |
| `SEED-0302` | 409 | 넘기기 | 자동 선발 전에 발표로 넘겼다. 선발 마감 뒤 약 1분 기다린다. |
| `SEED-0303` | 409 | 넘기기 | 단계를 건너뛰었다. 한 칸씩만 넘긴다. 발표 시각이 없는 차수가 묶음에 있을 때도 이 코드다. |
| `SEED-0304` | 409 | 넘기기 | 랜덤 배정 전에 랜덤 차수 조정 단계로 넘겼다. 3차 발표 뒤 약 1분 기다린다. |
| `SEED-0305` | 409 | 봇 지원 | 지원 기간(지원 시작부터 지원 마감 전까지)이 아니다. |
| `SEED-0306` | 409 | 봇 결정 | PM 결정 기간(지원 마감 뒤부터 선발 마감 전, 자동 선발 전까지)이 아니다. |
| `SEED-0307` | 404 | 요약, 봇, 넘기기 | 차수가 없다. 차수 ID를 확인한다. |

넘기기 요청에 `step`이 없으면 400이다. 봇 실행 중 개별 지원·결정이 운영 규칙에 걸리면 호출 전체를 실패시키지 않고 응답 `failed`에 운영 에러 코드별 개수로 센다. 다시 부르면 실패한 것만 다시 시도한다.
