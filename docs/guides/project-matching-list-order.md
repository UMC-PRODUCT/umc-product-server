# 팀 매칭 프로젝트 목록 정렬

## API 사용

기존 `GET /api/v1/projects`에서 새 정렬을 기본 적용한다. 새 요청 파라미터를 추가하지 않는다.

예: `/api/v1/projects?gisuId=1&chapterId=2&page=0&size=20`

기존 `parts`를 전달하면 해당 파트의 매칭 유형을 기준으로 모집 완료를 판단한다. `DESIGN`은 디자인 매칭, 개발 파트는 개발 매칭에 해당한다. 개발 파트를 하나 선택하더라도 완료 여부는 해당 프로젝트의 모든 개발 TO를 함께 본다.

파트 필터를 생략하면 해당 지부에서 현재 진행 중인 매칭 일정을 사용한다. 디자인·개발 매칭이 동시에 진행되면 현재 모집하는 두 유형의 TO가 모두 찬 프로젝트만 하단에 배치한다. 해당 유형의 TO 자체가 없는 경우에는 그 유형을 판단 대상에 추가하지 않는다.

기수·지부·학교·파트·모집 상태·검색어 필터와 조회 권한은 유지한다. PM 관리 목록의 상태별 정렬과 별도 GraphQL 목록의 정렬은 유지한다.

## 정렬 기준

1. 해당 지부의 매칭 기간에는 모집 중 프로젝트를 먼저, 모집 완료 프로젝트를 나중에 배치한다.
2. 각 그룹에서는 PM이 제출해 승인대기가 된 `submittedAt` 오름차순으로 정렬한다.
3. 제출 시각이 같으면 ID 오름차순으로 정렬한다.

요청한 `sort` 대신 이 순서를 적용한다. DB에서 전체 결과를 정렬한 후 페이지를 나누므로 페이지 경계에서도 순서가 유지된다.

## 모집 완료와 적용 기간

- 디자인 매칭은 디자인 TO, 개발 매칭은 레거시·신규 개발 파트의 TO를 판단한다.
- 현재 진행 중인 판단 대상 유형의 TO가 하나 이상 존재하고, 모든 해당 파트가 정원 이상 채워졌을 때 모집 완료다.
- 현재 공개 목록의 TO 계산과 동일하게 `ACTIVE` 팀원만 센다. 결과 발표 전 `PENDING_PUBLICATION`, 탈퇴·해제된 팀원은 포함하지 않는다.
- 하단 배치는 프로젝트 지부·매칭 유형의 첫 예정 차수 시작부터 마지막 예정 결과 발표까지 적용한다. 결과 발표 시각이 없는 차수는 결정 마감을 사용한다. 시작·종료 시각을 모두 포함하고 차수 사이에도 배치를 유지한다.
- 매칭 일정이 없거나 기간 밖이면 모집 완료 여부로 순서를 나누지 않고 제출순만 적용한다. 기간 판정 시각은 서버에서 지정한다.

## 제출 시각과 배포

`Project.submit()`에서 `submittedAt`을 기록한다. 이후 승인·정보 수정·소유권 양도로 이 시각을 변경하지 않는다.

기존 프로젝트는 이전 기수 데이터이므로 제출 시각을 임의로 복원하거나 보정하지 않는다. 컬럼은 nullable이며, 기록이 없는 항목은 호환 처리를 위해 앞쪽에서 ID순으로 정렬한다. 신규 제출부터 실제 제출 시각을 사용한다.

`V2026.10.25.00.00__add_project_submitted_at.sql`은 nullable 컬럼만 추가한다. 기존 Flyway 파일과 데이터는 수정하지 않는다. 운영·알파 배포는 저장소의 Flyway 절차에 따라 스키마 변경을 먼저 적용한 후 애플리케이션을 배포한다.
