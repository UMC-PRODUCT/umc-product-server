# 프로젝트 권한 정책

프로젝트, 프로젝트 지원용 폼, 프로젝트 지원서, 매칭 차수 도메인의 권한 정책을 정리합니다.

## 공통 원칙

| 항목 | 정책 |
| --- | --- |
| 참조 관계 삭제 제한 | 다른 도메인 또는 엔티티에서 참조 중인 데이터는 삭제할 수 없습니다. |
| 조회 공개 범위 | 별도 제한이 명시되지 않은 조회 API는 도메인별 정책을 따릅니다. |
| 운영진 권한 범위 | 기능마다 별도로 판단합니다. 프로젝트 관리 목록·등록은 아래 정책을 적용하며, 지원 현황·지원서 열람은 해당 절의 정책을 따릅니다. |
| 프로젝트 소유자 | `Project PO`는 프로젝트 생성, 수정, 삭제 및 관련 폼 관리의 핵심 권한자입니다. |

| 역할 | 권한 범위 |
| --- | --- |
| Plan 챌린저 | 본인이 `Project PO`인 프로젝트를 생성할 수 있습니다. |

| 지부장 | 소속 기수·지부의 Plan 챌린저를 `Project PO`로 지정할 수 있습니다. |
| 총괄단 | 소속 기수 전체 지부의 Plan 챌린저를 `Project PO`로 지정할 수 있습니다. |

| 최고관리자 | 기수·지부 제한 없이 Plan 챌린저를 `Project PO`로 지정할 수 있습니다. |
| Project PO | 본인이 담당하는 프로젝트, 프로젝트 지원용 폼, 지원서 합불 결정을 관리할 수 있습니다. |
| Sub-PO | 제출된 지원서 조회 권한을 가집니다. |
| 지원자 | 본인이 생성한 지원서를 조회, 수정, 삭제할 수 있습니다. |

## 프로젝트 권한

### 프로젝트 목록·상세의 PM 정보

`GET /api/v1/projects`와 `GET /api/v1/projects/{projectId}`는 로그인 사용자에게 PM의 `name`과 `schoolName`을 제공합니다. 상세의 `coProductOwners`도 같은 기준을 적용합니다. 비회원에게는 기존처럼 회원 ID·닉네임만 제공하고 실명·학교명은 null입니다. 로그인 여부는 인증된 사용자 정보로 판단하며 조회 파라미터로 지정할 수 없습니다.

목록에서 `chapterId`를 바꿀 때는 이전 지부의 `schoolIds`도 초기화해야 합니다. 지부·학교 조건은 AND로 적용하므로 서로 다른 지부·학교를 함께 보내면 200의 빈 목록을 반환합니다.

### 프로젝트 생성

프로젝트 생성 시 `Project PO`로 지정할 수 있는 대상은 요청자의 역할과 소속 범위에 따라 달라집니다.

| 요청자 역할 | `Project PO` 지정 가능 범위 |
| --- | --- |
| Plan 챌린저 | 본인만 지정 가능 |
| 학교 회장단·학교운영진 | 대리 등록 불가 |
| 지부장 | 소속 기수·지부의 Plan 챌린저 |
| 총괄단 | 소속 기수 전체 지부의 Plan 챌린저 |
| 중앙운영·교육국 일반 운영진 | 대리 등록 불가 |
| 최고관리자 | 모든 기수·지부의 Plan 챌린저 |

대상자는 요청 기수의 Plan 챌린저여야 합니다. 학교·중앙 일반 운영진이 Plan 챌린저를 겸하면 본인 프로젝트를 등록할 수 있으며, 다른 사람을 대신 등록하는 권한은 부여되지 않습니다.

### 프로젝트 등록용 PM 후보 조회

`GET /api/v1/projects/admin/pm-candidates?gisuId=6&keyword=토미&page=0&size=20`을 메인·보조 PM 선택에 사용합니다. 공통 회원 검색(`/api/v2/member/search`)과 별개 API이며 `gisuId`는 필수입니다.

- 지부장: 본인 기수·지부 전체 학교의 PM. 본인 학교로만 제한하지 않습니다.
- 총괄·부총괄: 소속 기수 전체 지부의 PM. 최고관리자: 선택한 기수 전체 지부의 PM.
- 일반 PM·학교 운영진·운영국원·교육국원 역할만으로는 403(`PROJECT-0012`)입니다. 이들에게 PM 본인 등록 권한을 추가하거나 제거하지 않습니다.
- 요청 기수의 활성 PLAN 챌린저 중 회원 계정도 활성이고, 해당 기수의 허용 학교에 연결된 인원만 반환합니다. 기존 프로젝트 보유 여부로 제외하지 않습니다.
- `keyword`는 이름·닉네임 부분 검색이며 앞뒤 공백과 영문 대소문자를 무시합니다. 생략하거나 공백이면 범위 내 전체 후보를 조회합니다.
- 표준 페이지 응답 `content`, `page`, `size`, `totalElements`, `totalPages`, `hasNext`, `hasPrevious`를 사용합니다. 기본 size는 20이며 이름·회원 ID 오름차순 고정입니다.
- 후보 필드는 `memberId`, `challengerId`, `name`, `nickname`, `schoolId`, `schoolName`입니다. 이메일·전화번호·프로필·권한·기타 기수 이력은 포함하지 않습니다.
- 프로젝트 생성 요청의 `productOwnerMemberId`에는 선택한 `memberId`를 전달합니다. 두 PM을 선택하면 프런트에서 동일인을 중복 선택하지 않도록 처리하고, 실제 등록은 기존 API의 검증을 따릅니다. 이 조회로 초안이나 팀원 정보를 생성하지 않습니다.

### 프로젝트 등록 완료

`POST /api/v1/projects/{projectId}/submit`은 작성자의 초안을 최종 제출하고 처리 후 상태를 반환합니다.

- 일반 PM의 제출은 `PENDING_REVIEW`(승인대기)로 전이합니다.
- 해당 프로젝트의 관리 권한이 있는 최고관리자·소속 기수 총괄단·담당 지부장이 제출하면 `IN_PROGRESS`(승인완료)로 전이하고 공개 목록에 반영합니다. 본인이 PM인 경우에도 같은 운영 권한을 적용합니다.
- 일반 중앙운영진·학교운영진 역할만으로는 자동 승인되지 않습니다. 해당 역할과 PM을 겸하면 본인 프로젝트를 승인대기로 제출할 수 있습니다.
- 운영진이 직접 등록할 때도 초안은 `DRAFT`로 저장합니다. 운영진 작성자는 해당 기수·지부 권한 범위에서 기존 `PUT /api/v1/projects/{projectId}/part-quotas`로 초안의 TO를 설정할 수 있습니다. PM에게 초안 TO 수정 권한을 부여하지 않습니다.
- 자동 공개는 기존 공개와 같은 필수 정보·TO·지원 폼 검증을 수행하고, 최종 등록 후의 지부 TO 합계가 인원 상한을 넘는지도 확인합니다.
- 지원 폼 공개와 프로젝트 승인을 한 트랜잭션에서 처리합니다. 검증이나 공개가 실패하면 상태와 제출 시각을 포함해 초안으로 롤백합니다.
- 제출 시 운영 권한을 다시 확인하며, 대리 작성한 운영진의 권한이 사라졌거나 다른 기수·지부 권한만 남으면 등록 완료를 거부합니다.

### 프로젝트 관리 목록

목록의 각 프로젝트는 썸네일 `thumbnailImageUrl`과 로고 `logoImageUrl`을 제공합니다. 로고가 등록되지 않았으면 `logoImageUrl`은 null이며, 이미지는 페이지 단위로 일괄 조회합니다.

`GET /api/v1/projects/me/managed?gisuId={gisuId}&chapterId={chapterId}`로 지부를 선택할 수 있습니다. `chapterId`는 선택 항목이며 생략하면 기존 조회 범위를 유지합니다. 선택한 지부는 역할·기수·소유자 조건 전체와 AND로 적용하며, 권한 밖·다른 기수·존재하지 않는 지부는 빈 목록을 반환합니다. 상태별 접근 범위와 정렬·페이지 합계에도 같은 필터를 적용합니다.

`GET /api/v1/projects/me/managed`는 요청 기수와 역할에 따라 다음 범위를 적용합니다.

| 역할 | 관리 범위 | 타인 프로젝트의 노출 상태 |
| --- | --- | --- |
| 최고관리자 | 모든 기수·지부 | 초안 제외 전체 |
| 총괄·부총괄 | 소속 기수 전체 지부 | 초안 제외 전체 |
| 지부장 | 소속 기수·지부 | 초안 제외 전체 |
| 중앙운영·교육국 일반 운영진 | 소속 기수 전체 지부 | 승인대기(`PENDING_REVIEW`)·등록완료(`IN_PROGRESS`) |
| PM | 본인 프로젝트 | 본인 초안을 포함한 전체 상태 |
| 학교 회장단·학교운영진 및 그 외 역할 | 해당 역할로 부여되는 범위 없음 | 없음 |

- 권한이 없는 기수나 역할로 조회하면 기존 응답 방식대로 200과 빈 페이지를 반환합니다.
- PM 겸직자는 본인 프로젝트 범위를 함께 적용합니다. 상태를 지정하면 기존 규칙대로 본인 초안을 추가로 포함합니다.
- 지부장과 중앙 일반 운영진을 겸하면 본인 지부 범위와 전체 지부의 승인대기·등록완료를 합칩니다. 범위를 합친 뒤 정렬과 페이지 나누기를 적용합니다.
- 중앙 일반 운영진의 목록 조회 권한은 승인·삭제·수동 배정 권한으로 확대되지 않습니다.

### 프로젝트 수정 및 삭제

| 행위 | 허용 대상 | 제한 사항 |
| --- | --- | --- |
| 기본 정보 수정 | 초안 작성자, 승인대기·등록완료 상태의 PM 또는 권한 범위 내 운영진 | 해당 지부의 n차 지원 기간에는 PM·운영진 모두 수정할 수 없습니다. 완료·중단 상태의 수정 제한은 유지합니다. |
| 삭제 | `Project PO` | 참조 관계가 있는 경우 삭제할 수 없습니다. |

기본 정보 수정 제한은 프로젝트의 기수·지부에 해당하는 차수를 기준으로 합니다. 지원 시작·마감 시각을 모두 포함하며, 지원 시작 전과 마감 후 판정·결과 발표 기간에는 기존 권한·상태 조건에 따라 수정할 수 있습니다. 랜덤 매칭은 지원 기간으로 보지 않습니다. 초안·승인대기도 같은 기간 제한을 적용합니다.

`PATCH /api/v1/projects/{projectId}`가 지원 기간에 호출되면 409(`PROJECT-0025`)를 반환하고 정보를 변경하지 않습니다. 화면 권한 조회의 `canEditInfo`에도 같은 제한을 반영합니다. 소유권 양도·공동 PM 관리 등 다른 EDIT 기능에는 이 기간 제한을 확대하지 않습니다.

### 프로젝트 조회

| 조회 대상 | 공개 범위 | 비고 |
| --- | --- | --- |
| 프로젝트 자체 조회 | Public API | 인증 또는 역할 제한 없이 공개합니다. |
| 매칭 현황 조회 | Public API | `ProjectMember` 조회를 포함해 공개합니다. |

현재 상세 조회는 공개 API인 `GET /api/v1/projects/{projectId}`로 제공하며, 관리 전용 상세 API는 분리되어 있지 않습니다. 관리 전용 상세를 구분할 기준은 PM·프런트와 확인 후 반영하며, 이번 관리 목록·등록 권한 변경에서 공개 상세의 동작을 변경하지 않습니다. 초안 공개 상세 접근 문제는 [별도 후속 사항](../backlog/project-draft-access-policy.md)으로 남깁니다.

## 프로젝트 지원용 폼 권한

프로젝트 지원용 폼은 프로젝트 지원서 생성 가능 여부를 판단하는 정책 기준입니다.

| 행위 | 허용 대상 | 비고 |
| --- | --- | --- |
| 생성 | `Project PO` | 본인이 담당하는 프로젝트에 대해서만 가능합니다. |
| 수정 | `Project PO` | 지원 가능 파트, 차수 등 지원 정책 변경 시 영향을 받는 지원서 정책을 함께 검토해야 합니다. |
| 삭제 | `Project PO` | 참조 관계가 있는 경우 삭제할 수 없습니다. |

## 프로젝트 지원서 권한

### 지원서 생성

지원서 생성은 프로젝트 지원용 폼의 정책에서 허용한 파트의 챌린저에게만 허용됩니다.

| 조건 | 정책 |
| --- | --- |
| 지원 가능 파트 | 지원용 폼에서 제한한 파트에 포함된 챌린저만 지원할 수 있습니다. |
| 기수 내 기존 팀 소속 여부 | 이미 해당 기수에 소속된 팀이 있으면 중복 지원할 수 없습니다. |
| 동일 차수 중복 제출 | 이미 동일한 차수에 제출한 지원서가 있으면 중복 지원할 수 없습니다. |
| DB 제약 | 동일 차수 중복 제출은 Unique Key로도 제한됩니다. |

> 1차 매칭에서 팀이 결정된 경우 2차 매칭에 지원할 수 없습니다. 단, 1차에서 강제 배정되었을 수도 있으므로 팀 소속 여부 판단 로직은 배정 경로와 상태를 함께 고려해야 합니다.

### 지원서 조회

| 조회자 | 조회 가능 범위 |
| --- | --- |
| 지원자 본인 | 본인이 제출한 지원서 |
| `Project PO` | 본인 프로젝트에 제출된 지원서 |
| `Sub-PO` | 본인이 `Sub-PO`로 지정된 프로젝트에 제출된 지원서 |
| 지부장급 이상 운영진 | 권한 범위 내 지원서 |

### 지원서 수정 및 삭제

| 행위 | 허용 대상 | 제한 사항 |
| --- | --- | --- |
| 수정 | 지원서 생성자 | 본인의 `DRAFT` 또는 `SUBMITTED` 지원서만 수정할 수 있습니다. 제출본은 해당 지원 차수의 지원 기간에만 수정할 수 있습니다. |
| 삭제 | 지원서 생성자 | 본인이 생성한 지원서만 삭제할 수 있습니다. |

`APPLY-002` (`PUT /api/v1/projects/{projectId}/applications/{applicationId}`)는 답변 전체를 교체하며, 지원 파트·프로젝트·차수는 변경하지 않습니다.

- `DRAFT`는 기존과 같이 필수 답변 누락을 허용하며, 초안 임시저장에 새 기간 제한을 추가하지 않습니다.
- `SUBMITTED`는 해당 지원서 차수의 지원 기간(`startsAt <= now <= endsAt`) 검사 시점을 기준으로 수정할 수 있습니다. 다른 차수가 모집 중이어도 해당 차수가 마감되면 수정할 수 없습니다.
- 제출본 수정은 제출과 같은 형식·필수 답변·파트별 허용 문항 검증을 적용합니다. 검증 실패 시 기존 제출본을 유지합니다.
- 수정 성공 시 답변을 즉시 반영하며, 지원서와 폼 응답의 제출 상태·최초 제출 시각을 유지하고 마지막 저장 시각만 갱신합니다. 재제출은 필요하지 않습니다.
- `APPROVED`, `REJECTED`, `CANCELLED` 상태는 수정할 수 없습니다. 기존 `APPLY-003`의 초안 제출 정책과 PM·운영진 열람 시점은 유지합니다.

### 지원서 합불 결정

| 행위 | 허용 대상 | 제한 사항 |
| --- | --- | --- |
| 합격·불합격·대기 판정 | `Project PO`, 해당 기수 총괄·부총괄, 해당 기수·지부의 지부장, 최고관리자 | 해당 차수 매칭기간(지원 마감 후 ~ 결정 마감)에만 가능하며 최고관리자도 같은 시간 제한을 받습니다. 일반 중앙운영진·`Sub-PO`는 판정할 수 없습니다. 요청 URL의 프로젝트가 지원서의 프로젝트와 다르면 404입니다. |
| 지원 현황 조회 | `Project PO`, `Sub-PO`, 운영진 | 지원자 본인에게는 전체 지원 현황 조회 권한이 없습니다. 목록 조회 권한이 있는 `Project PO`·`Sub-PO`·최고관리자·총괄단·일반 중앙운영진·지부장·학교 운영진은 지원 기간 중에도 제출된 지원자 목록을 실시간으로 봅니다. |
| 지원서 열람 | `Project PO`, `Sub-PO`, 운영진 | 지원서 답변·첨부 열람은 `Project PO`·`Sub-PO`·지부장·학교 회장단 모두 지원 마감 후부터입니다. 최고관리자와 같은 기수 총괄단만 지원 기간 중에도 열람할 수 있습니다. |

### 지원자 목록 조회 범위

프로젝트별 조회(`GET /api/v1/projects/{projectId}/applications`)와 일괄 조회(`GET /api/v1/projects/applications?projectIds=...`)는 같은 범위를 적용합니다.

| 역할 | 조회 범위 |
| --- | --- |
| 최고관리자 | 기수·지부 제한 없음 |
| 총괄·부총괄 | 해당 기수 전체 지부 |
| 중앙 운영국원·교육국원 | 해당 기수 전체 지부 |
| 학교 회장·부회장·파트장·기타 운영진 | 소속 지부 |
| `Project PO`, `Sub-PO` | 본인 프로젝트 |
| 지부장 | 소속 기수·지부 |

학교 운영진의 소속 지부는 역할의 학교와 프로젝트 기수의 학교–지부 매핑으로 확인합니다. 같은 지부의 다른 학교 PM 프로젝트도 조회할 수 있습니다. 다른 기수의 학교 역할은 조회 권한을 부여하지 않습니다.

권한이 없는 프로젝트는 빈 목록을 반환하며, 일괄 조회는 요청한 프로젝트 ID를 응답 key로 유지합니다. 목록 조회 권한은 지원서 상세 조회·합불 권한을 추가하지 않습니다.

### 지원자 목록의 합불 결과 표시

단건·일괄 목록 모두 지원서가 속한 차수의 PM 결정 기간(`endsAt < now <= decisionDeadline`)에는 담당 PM·해당 기수 총괄·부총괄·해당 기수·지부의 지부장·최고관리자에게 실제 합불 결과를 즉시 표시합니다. 다른 조회자는 합격·불합격을 포함한 해당 차수의 지원서를 `SUBMITTED`(대기)로 보고, `statusChangedAt`은 null로 받습니다.

결정 기간이 끝난 이전 차수의 결과는 그대로 표시합니다. 프로젝트 상태는 결과 노출 판단에 사용하지 않으며, 저장된 지원서 상태도 변경하지 않습니다. `status` 필터는 표시 상태에 적용하므로, 결과가 가려진 지원서는 대기 필터에 포함되고 합격·불합격 필터에서는 제외됩니다. 본인 지원 내역과 지원서 상세의 기존 결과 공개 규칙은 유지합니다.

### 매칭 차수 경과 시 자동 합불 처리

지원서의 매칭 차수가 경과했는데 `Project PO`가 합불을 결정하지 않은 경우, 최소 선발 규칙에 따라 자동 합불 처리를 수행해야 합니다.

1~3차는 결정 마감 후 기본 1분 뒤 자동 선발합니다. 발표 시각이 있는 차수는 선발한 멤버를 `PENDING_PUBLICATION`으로 생성하고, 지원서는 PM의 마지막 결정값을 유지합니다. 발표 작업에서 멤버를 `ACTIVE`로 변경하고 지원서 합불을 반영한 뒤 지원자에게 결과를 공개합니다. 발표 시각이 없는 기존 차수는 자동 선발 시 즉시 반영합니다.

| 항목 | 정책 |
| --- | --- |
| 자동 선발 기준 | 기존 합격자를 유지하고, 최소 선발 인원에 모자란 만큼 미판정(대기) 지원자 중에서 랜덤으로 합격 처리합니다. 그래도 모자라면 불합격 지원자 중에서 랜덤으로 합격 처리합니다. |
| 자동 탈락 기준 | 합격자로 뽑히지 않은 나머지 지원자는 불합격 처리합니다. |
| PM 판정 | PM은 결정 마감 전까지 합격·불합격·대기(되돌리기)를 자유롭게 바꿀 수 있고, 불합격 처리에 최소 선발 인원 제한이 없습니다. |
| 규칙 차이 | 기획-디자인 매칭과 기획-개발 매칭의 최소 선발 규칙은 서로 다릅니다. |
| 참고 문서 | [10th UMC PLAN(팀장) 필독 공지](https://www.notion.so/10th-UMC-PLAN-33ab57f4596b81ae927ec25d0892849b?pvs=21)의 선발 필수 규칙을 확인해야 합니다. |

예시:

| TO | 지원자 수 | 최소 선발 인원 | 자동 처리 결과 |
| --- | --- | --- | --- |
| 4명 | 5명 | 2명 | 기존 합격자가 없으면 2명 랜덤 합격, 3명 불합격 |

랜덤 매칭은 지원서를 받지 않고 같은 지부·유형의 3차 결과 공개 후 잔여 정원으로 배정합니다. `PLAN_DESIGN`과 `PLAN_DEVELOPER` 모두 선발한 멤버를 `PENDING_PUBLICATION`으로 생성하고, 발표 작업에서 `ACTIVE`로 변경합니다.

운영진 조정 명단(`view=ADJUSTMENT`)은 수동 배정 권한(슈퍼어드민·해당 기수 총괄단·담당 지부장)이 있어야 조회할 수 있습니다.

## TO 관리 권한 및 수정 기간 (#1415)

TO 관리의 최신 기준은 아래 표와 [연동 가이드](project-quota-management.md)를 따릅니다.

| 역할 | 조회·저장 범위 |
| --- | --- |
| 최고관리자 | 전체 기수·지부 |
| 총괄단 | 소속 기수 전체 지부 |
| 운영국원·교육국원 (`CENTRAL_OPERATING_TEAM_MEMBER`, `CENTRAL_EDUCATION_TEAM_MEMBER`) | 소속 기수 전체 지부 조회만 허용, 수정·저장 불가 |
| 지부장 | 소속 기수 전체 지부 조회, 본인 지부만 수정·저장 |
| 학교운영진·PM | 해당 역할만으로는 TO 관리 조회·저장 불가 |

해당 지부의 디자인·개발 중 첫 매칭 시작 이후에는 PM을 포함한 모든 파트 TO 설정을 계속 잠급니다. 3차 마감·랜덤 매칭·운영진 조정·최종 발표 이후에도 다시 허용하지 않습니다. 매칭 시작 전에는 실제 배정 인원(발표 대기 포함) 미만 축소와 지부의 해당 파트 인원을 초과하는 합계를 거부하며, 인원보다 TO가 부족한 경우는 저장할 수 있습니다. 랜덤 매칭 실행 후 운영진 조정 기간에는 설정 TO를 그대로 유지하면서 초과 배정을 허용합니다. 최종 발표 시 해제 예약자를 제외한 확정 활동 인원이 TO보다 많으면 해당 매칭 유형의 파트 TO를 그 인원까지 자동 증가시키며, 기존 TO를 줄이지 않습니다. 일반 차수의 수동 배정은 기존 정원·미반영 합격자 제한을 유지합니다.
