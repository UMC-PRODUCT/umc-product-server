# 프로젝트 TO 관리 연동

## API

| 기능 | 요청 |
| --- | --- |
| 화면 조회 | `GET /api/v1/projects/admin/part-quotas?gisuId={gisuId}` |
| 지부·검색·학교 선택 | 위 GET에 `chapterId`, `keyword`, `schoolId` 선택 전달 |
| 변경 셀 일괄 저장 | `PATCH /api/v1/projects/admin/part-quotas` |

최고관리자는 모든 기수·지부, 총괄·부총괄은 소속 기수 전체 지부, 지부장은 소속 기수·지부에 접근한다. 일반 중앙운영진·학교 운영진·PM 역할만으로는 이 관리 API에 접근할 수 없다. 권한이 있는 운영진 역할을 겸하면 해당 범위를 적용한다.

첫 GET에는 `gisuId`만 전달해도 된다. 서버가 접근 가능한 첫 지부를 선택하고 지부 탭·학교 선택지·표·합계·편집 가능 여부를 함께 반환한다. 요청한 지부에 권한이 없으면 403이며, 지부가 전혀 없는 기수는 `chapterId: null`과 빈 배열을 반환한다.

## 조회 응답과 화면 대응

응답은 기존 공통 성공 응답의 `result` 안에 들어간다. 공통 Jackson 설정에 따라 **ID·인원·TO 등 모든 숫자는 JSON 문자열**이다. 계산과 입력에는 `Number(value)`로 변환하고, boolean은 그대로 사용한다.

| 필드 | 사용처 |
| --- | --- |
| `gisuId`, `chapterId`, `chapterName` | 현재 선택 범위 |
| `chapters[]` | 접근 가능한 지부 탭 |
| `schools[]` | 선택한 지부의 학교 필터 |
| `columns[]` | 파트·라벨·공통 편집 권한·재개 시각 |
| `summary[]` | 지부 전체 프로젝트의 파트별 인원·TO 합계·과부족 |
| `filteredSummary[]` | 검색·학교 필터에 해당하는 프로젝트의 파트별 합계 |
| `totals`, `filteredTotals` | 각 합계의 전체 파트 총인원·총TO·과부족 |
| `totalProjectCount`, `filteredProjectCount` | 지부 전체/필터 프로젝트 수 |
| `projects[]` | 프로젝트명·ID순 표 전체 목록. 내부 스크롤에 사용 |
| `projects[].schoolId`, `schoolName` | 프로젝트 PM의 소속 학교 |
| `projects[].cells[]` | 파트별 입력값·현재 인원·최소 TO·편집 권한 |
| `projects[].totalQuota` | 프로젝트의 파트 TO 합계 |

인원 현황은 해당 기수의 활동 중인 챌린저 중 수강 파트가 있는 인원을 사용하고 매칭 지부 이동을 반영한다. 수강 없이 기수에만 소속된 운영진(part=null)은 파트별 모집 가능 인원과 전체 합계에서 제외한다. 새 기수의 기본 열은 `columns[].label`에 `PM`, `Design`, `Web PE`, `Mobile PE`로 반환하며, 과거 파트의 인원이나 TO가 있으면 해당 열도 포함한다. 표의 각 행은 프로젝트이며 학교는 필터다.

`summary`와 `filteredSummary`의 `availableCount`는 모두 지부 전체의 파트 인원이다. 학교 필터는 프로젝트를 골라 보는 용도이며, 모집 가능한 인원을 PM의 학교 인원으로 제한하지 않는다. `difference = allocatedQuota - availableCount`이며, `allocationStatus`는 `SHORTAGE`, `BALANCED`, `EXCESS`다. 검색 결과가 비어도 지부 전체 합계는 유지한다.

셀 필드:

- `quota`: 편집할 TO. 미모집 파트는 0. PM TO가 아직 저장되지 않았으면 현재·발표 대기 PM 인원(소유자 포함)을 기본값으로 표시한다.
- `currentCount`: 현재 활동 팀원 수. PM은 소유자를 포함하고 공동 PM과 중복 집계하지 않는다.
- `minimumQuota`: 발표 대기까지 포함하되, 해당 파트의 랜덤 조정 차수에 해제 예약된 인원은 제외한 배정 인원. PM은 소유자를 포함한다. 랜덤 배정 완료 후 조정 시작부터 최종 공개 전까지 이 기준을 적용하며, `currentCount`는 공개 명단 기준을 유지한다.
- `canEdit`: `{allowed, reasonCode, reason}`. 입력 활성화와 잠금 설명에 사용한다.

`columns[].canEdit`는 모든 파트에 공통인 잠금 상태다. 해당 지부의 디자인·개발 중 먼저 시작하는 매칭의 시작 시각부터 PM을 포함한 모든 TO 설정을 계속 잠근다. 3차 마감·랜덤 매칭·운영진 조정·최종 발표 후에도 다시 열리지 않으며, `editableAfter`는 null이다. 시작 이후에는 `PART_QUOTA_MATCHING_IN_PROGRESS` 사유를 반환한다. 일정이 없거나 아직 시작 전이면 수정할 수 있고, 일반 차수 없이 랜덤 일정만 남아 있어도 그 시작 이후에는 잠근다.

## Web PE·Mobile PE 모집 파트 전환

TO 표의 `WEB_PRODUCT_ENGINEER`와 `MOBILE_PRODUCT_ENGINEER` 셀은 모두 반환하며, 미모집 파트의 TO는 0이다. 프로젝트 등록 때 선택했던 파트로 수정 대상을 제한하지 않는다.

- 두 파트 중 하나만 양수로 저장할 수 있다. 프런트는 Web TO가 양수이면 Mobile 입력을 비활성화하고, Mobile TO가 양수이면 Web 입력을 비활성화한다. 둘 다 0이면 둘 다 입력 가능하다. 미저장 입력값으로 즉시 판단하며 기간·권한에 따른 `canEdit` 제한도 함께 적용한다.
- Web → Mobile 전환은 같은 프로젝트의 `entries`에 `WEB_PRODUCT_ENGINEER: 0`, `MOBILE_PRODUCT_ENGINEER: N`을 함께 전달한다. 반대 방향도 같다. 기존 양수 TO를 생략하면 그대로 보존되므로 다른 파트만 추가하면 `PROJECT-0255`로 거부한다.
- 기존 파트의 발표 대기를 포함한 최소 배정 인원이 남아 있으면 TO를 0으로 바꿀 수 없다. 기간·권한·지부 인원 상한 검증도 그대로 적용한다.
- 등록 Step 2 상세와 프로젝트 카드의 `partQuotas`는 같은 저장 데이터를 사용한다. 저장 후 관리 표와 해당 상세·목록 API를 재조회하거나 프런트 캐시를 갱신하면 변경된 모집 파트·TO가 반영된다. 상세·카드의 `partQuotas`에서는 TO 0으로 제거한 파트가 제외된다.

## 저장 예시

변경한 셀만 전달한다. 아래 요청은 프로젝트 101의 디자인 TO를 2로, 프로젝트 102의 디자인 TO를 0으로 바꾼다. 다른 셀과 프로젝트는 그대로 유지한다.

```json
{
  "gisuId": "1",
  "chapterId": "10",
  "projects": [
    { "projectId": "101", "entries": [{ "part": "DESIGN", "quota": 2 }] },
    { "projectId": "102", "entries": [{ "part": "DESIGN", "quota": 0 }] }
  ]
}
```

숫자·숫자 문자열 모두 요청할 수 있다. PM TO도 `part: "PLAN"`으로 수정한다. `quota: 0`은 모집 TO를 제거하지만 팀원은 삭제하지 않는다. 배정된 인원이 있으면 그 인원 미만으로 줄일 수 없다.

저장 성공 시 `result.updatedProjectIds`에 변경 대상 ID 목록을 반환한다. 이후 같은 필터의 GET을 다시 호출해 표·합계·최소 TO·권한을 갱신한다. 초기화 버튼은 마지막 GET 결과로 프런트의 미저장 입력을 되돌리며, 서버 삭제 요청을 보내지 않는다.

## 검증과 동시 저장

- 해당 지부 전체 첫 매칭 시작부터 모든 파트의 TO 변경을 계속 차단한다. 차수 사이·3차 종료 후·운영진 조정 기간에도 잠금을 유지한다. 같은 값만 저장하는 요청은 기존처럼 허용한다.
- 랜덤 매칭 실행 후 운영진 조정 기간의 수동 배정은 설정 TO를 초과할 수 있다. 이는 팀원 배정에만 적용하며 TO 설정을 수정하거나 잠금을 해제하지 않는다. `currentCount`나 `minimumQuota`가 저장 TO보다 클 수 있다.
- 지부의 파트별 인원을 넘는 TO 합계는 거부하고 부족은 허용한다. 필터로 숨겨진 프로젝트의 TO도 전체 지부 상한에 포함한다.
- 모든 변경을 합친 최종 상태를 검증하므로 프로젝트 사이의 TO 이동을 한 번에 저장할 수 있다. 하나라도 실패하면 전체 요청을 롤백한다.
- 기수 단위 매칭 잠금으로 수동 배정·자동 선발·지부 이동과 정원 변경을 직렬화한다. 발표 대기 배정도 최소 TO에 포함해 이미 확보한 자리를 줄이지 않는다. 해제 예약자는 조회·PATCH·PUT의 최소 TO에서 동일하게 제외하고, 해제 예약을 취소하면 다시 포함한다.
- 기존 `PUT /api/v1/projects/{projectId}/part-quotas`에도 같은 기간·인원 상한·기존 배정 인원 검증을 적용한다. 이 PUT은 기존대로 전체 교체이며 입력값은 1 이상이다. 운영진 직접 등록 시에는 해당 기수·지부의 운영 권한을 가진 작성자만 이 PUT으로 본인 초안의 TO도 설정할 수 있다. 초안은 관리 표 합계에 포함하지 않고 최종 등록 시 인원 상한을 검증한다. 일반 PM은 초안 TO를 수정할 수 없다. 관리 화면은 변경 셀을 보존하는 PATCH를 사용한다.

| HTTP | 코드 | 의미 |
| --- | --- | --- |
| 409 | `PROJECT-0250` | 전체 첫 매칭 시작 이후 TO 설정 변경 불가 |
| 409 | `PROJECT-0251` | 지부 파트 인원보다 TO 합계가 많음 |
| 409 | `PROJECT-0252` | 기존 배정 인원보다 TO가 적음 |
| 400 | `PROJECT-0253` | ADMIN 등 직접 수정할 수 없는 파트 |
| 400 | `PROJECT-0254` | 중복 프로젝트·파트, 잘못된 대상·입력 |
| 400 | `PROJECT-0255` | Web PE와 Mobile PE를 동시에 모집하도록 저장함 |
| 403 | `PROJECT-0012` 등 기존 권한 오류 | 역할·기수·지부 권한 없음 |

입력 형식 오류는 공통 400 검증 오류다. 서버의 거부 응답을 받으면 미저장 입력을 유지해 수정할 수 있게 하고, 필요하면 최신 GET을 재조회한다. 서버가 다른 프로젝트의 값까지 일부 저장한 상태로 반환하지 않는다.

## 저장 모델

기존 `project_part_quota`를 사용하며 이 변경에는 Flyway 파일이나 DB 스키마 변경이 없다. PM·프로젝트 기본 정보·팀원 관리의 다른 권한을 TO 편집 권한으로 확대하지 않는다.
