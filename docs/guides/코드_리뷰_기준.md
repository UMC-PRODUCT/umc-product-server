## 개요

PR을 리뷰할 때 쓰는 기준입니다. 사람 리뷰어와 AI 리뷰어가 같이 씁니다.

규칙 문장의 원본은 루트 [`AGENTS.md`](../../AGENTS.md)에 있고, 이 문서는 규칙을 번호(`ARCH-05` 같은)로만 가리킵니다.
규칙을 바꾸려면 `AGENTS.md`를 고치고, 이 문서는 우선순위·강제 수단·리뷰 절차만 고칩니다.

## 리뷰하는 순서

1. 변경 경로에 해당하는 루트 `AGENTS.md` 규칙과, 변경 경로에 가까운 하위 `AGENTS.md`를 읽습니다.
2. 지적은 아래 형식으로 남깁니다.

```text
[P2][ARCH-05] 다른 도메인 Repository를 직접 주입합니다.
문제: 이 줄이 member 도메인의 Repository를 주입해 도메인 경계를 넘습니다.
언제: member 도메인의 저장 구조를 바꾸면 이 서비스도 함께 깨집니다.
수정: member 도메인의 GetMemberUseCase를 주입합니다.
```

PR에서는 지적을 문제의 코드에 바로 답니다. 다는 위치와 문장은 [`PR_글쓰기_기준.md`](PR_글쓰기_기준.md)를 따릅니다.

하위 `AGENTS.md`의 규칙은 번호가 없으므로 `[P3][notification/AGENTS.md#ANTI-PATTERNS]`처럼 `<경로>#<절>`로 가리킵니다.
루트와 하위 어디에도 해당하는 규칙이 없을 때만 `규칙 후보`라고 적습니다. 같은 `규칙 후보` 지적이 반복되면 `AGENTS.md`에 새 규칙으로 올릴지 논의합니다.

## 지적 우선순위

| 우선순위 | 대상 |
|---|---|
| P1 | 보안, 데이터 손실, 심각한 버그 |
| P2 | 아키텍처, 성능, 확장성 |
| P3 | 코드 품질, 컨벤션 |
| P4 | 다른 방법 제안 |
| P5 | 오타, 질문 |

## 규칙별 기본 우선순위와 강제 수단

"강제 수단"은 사람이 놓쳐도 무엇이 막아 주는지입니다. "리뷰"라고 적힌 규칙은 리뷰에서만 지켜집니다.

기본 우선순위는 번호 앞부분으로 정하고, 다른 규칙만 예외로 적습니다. 새 규칙은 예외로 적지 않으면 기본값을 따릅니다.

| 규칙 | 기본 우선순위 |
|---|---|
| `AUTHZ` | P1 |
| `ARCH` | P2 |
| `CONV`, `TEST`, `GIT` | P3 |

| 예외 | 우선순위 | 이유 |
|---|---|---|
| CONV-09 | P1 | 인증 코드·토큰 로그 노출은 보안 문제 |
| CONV-01, CONV-19 | P2 | 트랜잭션 경계와 N+1은 성능·데이터 문제 |

테스트나 빌드가 일부 범위를 막는 규칙입니다. 표에 없는 규칙과 범위는 리뷰에서만 지켜집니다.

| 규칙 | 막는 범위 | 강제 수단 |
|---|---|---|
| ARCH-03, ARCH-05 | `chat`과 `community` 패키지 사이 의존 | `ChatCommunityDependencyArchTest` (ArchUnit) |
| ARCH-05 | `:blog` 모듈이 다른 도메인 내부를 쓰는 것 | `BlogModuleBoundaryTest` |
| ARCH-07 | community 도메인·어댑터의 `@OneToMany` | `CommunityThreadArchitectureTest` (소스 검사) |
| CONV-06 | community admin 경로 | `CommunityThreadArchitectureTest` (소스 검사) |
| CONV-20 | `V*__*.sql` 이름인 파일끼리의 버전 중복 | `./gradlew check`의 `checkDuplicateFlywayMigrationVersions` |

CONV-20의 이름 형식 자체는 막지 못합니다. 위 검사는 `V*__*.sql`에 맞는 파일만 보므로 `V..._foo.sql`(밑줄 하나) 같은 이름은 검사에서 빠지고, Flyway도 그 파일을 적용하지 않습니다. 이름 형식은 리뷰가 확인합니다.

줄 길이, 들여쓰기 같은 서식은 Spotless와 Checkstyle이 `./gradlew check`에서 막으므로 리뷰에서 지적하지 않습니다.

## 기준을 고치는 방법

리뷰 기준은 리뷰 결과에 따라 계속 바뀝니다. 리뷰와 처리 기록은 PR에 남으므로 이 문서에 따로 모으지 않습니다.

1. 같은 지적이 서로 다른 PR 두 곳 이상에서 받아들여지면, 테스트나 린트로 막을 수 있는지 봅니다. 막았다면 위 표의 "강제 수단"을 고칩니다. pstack을 쓴다면 `/pstack:correct`가 이 작업을 합니다.
2. `규칙 후보` 지적이 반복되면 `AGENTS.md`에 새 번호로 규칙을 추가합니다. 번호는 다시 쓰지 않습니다.
3. 같은 이유로 반영하지 않은 지적이 반복되면, 그 판단을 `AGENTS.md` 규칙이나 이 문서의 기준으로 올립니다.
4. 한 달에 한 번 최근 PR의 리뷰 스레드를 보고 이 문서를 점검합니다.

## AI 리뷰

`develop`으로 가는 PR을 열면 CI(`.github/workflows/ai-review.yml`)가 `.claude/skills/umc-review`로 리뷰를 남깁니다. 머지를 막지는 않습니다. 릴리스, 봇, 포크 PR과 draft는 건너뜁니다.

- **다시 리뷰받기**: 푸시만으로는 다시 돌지 않습니다. 새 커밋을 올린 뒤 PR에 `ai-review` 라벨을 붙이면 다시 돌고, 끝나면 라벨은 저절로 떨어집니다. 이미 리뷰한 커밋은 다시 돌지 않습니다.
- **PR 전에 미리 보기**: 로컬에서 `/umc-review`를 부르면 결과만 보여 주고 GitHub에는 아무것도 남기지 않습니다.
- **쓰는 방법**: 코멘트 모양과 문장은 [`PR_글쓰기_기준.md`](PR_글쓰기_기준.md)를 따릅니다. AI 리뷰 결과는 PR 본문에 쓰지 않습니다.
- **계정**: 리뷰어를 본문 첫 줄(`🐛 버그·보안 리뷰어`, `🧹 코드 품질 리뷰어`)로 구분합니다. 승인과 변경 요청은 사람 몫이라 AI는 `COMMENT`만 씁니다.

리뷰가 달리면 PR 작성자가 처리합니다.

1. **지적을 처리합니다.** 반영하면 커밋을 push하고 줄 코멘트에 `반영했습니다: <커밋 SHA>`와 바뀐 내용을 답합니다. 반영하지 않으면 이유를 답합니다. 답한 스레드는 해결 처리하고, 사람이 정해야 하는 지적은 열어 두고 그렇게 적습니다.
2. **처리 결과 표를 남깁니다.** `## 리뷰 처리 결과` 코멘트 하나에 `| # | 리뷰어 | 지적 | 처리 |` 행을 지적마다 적습니다.
3. **필요하면 한 번 더 봅니다.** 반영이 동작을 바꿨으면 `ai-review` 라벨로 다시 리뷰받습니다. 두 번째 라운드 뒤에 남은 것은 사람 리뷰에 맡깁니다.
