# 운영진 수동 배정·매칭 해제 (#1400)

## API

| 기능 | 메서드·경로 |
|---|---|
| 후보 조회 | `GET /api/v1/projects/admin/{projectId}/members/candidates?part=DESIGN` |
| 수동 배정 | `POST /api/v1/projects/admin/{projectId}/members` |
| 매칭 해제 | `DELETE /api/v1/projects/admin/{projectId}/members/{memberId}?reason=사유` |

배정 본문은 기존 팀원 추가 요청과 동일한 `memberId`, `part`를 사용한다.
후보 조회는 `keyword`, `page`, `size`를 지원하며 회원 ID 오름차순으로 반환한다.

## 권한과 검증

- 슈퍼어드민·해당 기수 총괄단은 전체 지부, 해당 기수 지부장은 담당 지부를 관리한다.
- 수동 배정 대상은 등록완료(IN_PROGRESS) 프로젝트와 해당 기수의 활동 중인 디자인·개발 챌린저다.
- 후보의 실제 파트와 매칭 지부가 요청과 일치해야 한다. 매칭 지부 이동도 반영한다.
- ACTIVE·PENDING_PUBLICATION 팀원 또는 합격 지원서가 있으면 배정 후보에서 제외한다. 대상 유형의 조정 명단에서 해제 예약된 팀원과 그 연결 지원서는 중복 검사에서 제외한다.
- 파트 TO에서 ACTIVE·PENDING_PUBLICATION 인원을 차감하되, 대상 조정 차수에 해제 예약된 인원은 제외한다. 아직 팀원이 아닌 APPROVED 지원자는 TO에서 차감하지 않는다. TO 초과 시 409로 거부한다.
- 해당 지부의 디자인·개발 중 하나라도 다음 기간에 해당하면 두 유형 모두 수동 배정·해제를 할 수 없다.
  - 1~3차 결정 마감부터 해당 결과 공개 완료 전까지
  - 3차 결과 공개 완료 후 운영진 조정 시작 전까지
  - 운영진 조정 종료부터 최종 결과 공개 완료 전까지
- 조정 기간에도 랜덤 매칭이 완료되지 않았으면 수동 배정·해제를 할 수 없다. 그 외 기간과 최종 결과 공개 이후에는 즉시 반영할 수 있다.
- 후보 조회는 변경 불가 기간에도 허용한다. 완료·중단 프로젝트 변경과 메인 PM 제거는 기존처럼 거부한다.

## 기존 API와 화면 연동

기존 팀원 추가·삭제 API도 일반 파트에 대해서는 같은 운영진 매칭 정책을 적용한다. 상태 변경 API는 기존 즉시 반영 정책을 유지하며 배정·해제 기간 제한을 적용하지 않는다.
PM의 보조 PM(PLAN) 관리와 지원서 합격 판정은 기존 권한을 유지한다. 보조 PM 추가 시 실제 PLAN 챌린저인지 검증한다.

프로젝트 권한 응답의 `member.canCreate`, `member.canDelete`는 기존 보조 PM 관리 용도로 유지한다.
일반 팀원 수동 매칭 버튼은 `member.canAssign`, `member.canUnassign`을 사용한다. 권한·프로젝트 상태와 해당 지부의 공통 변경 가능 기간을 반영한다.
각 필드는 기존 capability와 같은 `allowed`, `reasonCode`, `reason` 형식이다. 기간 제한 시 `PROJECT_MANUAL_MATCHING_NOT_ALLOWED_IN_PERIOD` 사유를 반환한다. 파트별 잔여 TO는 설정된 TO와 조회한 팀원 명단으로 확인하며, 배정 대상의 자격과 TO는 실제 배정 요청에서 다시 검증한다.

매칭 결과 시트는 기존 `GET /api/v1/projects/members?projectIds=...`에 `view`를 지정한다.

- `PUBLISHED`(기본값): 현재 공개된 명단을 반환하며, 권한이 없거나 존재하지 않는 프로젝트는 제외한다.
- `ADJUSTMENT`: 랜덤 매칭 완료 후 조정 시작부터 최종 공개 전까지 미공개 배정을 포함하고 해제 예약자를 제외한다. 조정 종료 후에도 조회할 수 있으며, 그 외에는 공개 명단을 반환한다.
- `ADJUSTMENT`는 슈퍼어드민·해당 기수 총괄단·담당 지부장만 조회할 수 있다. 지부장은 프로젝트 기수와 담당 지부가 일치해야 하며, 하나라도 권한이 없으면 요청 전체가 403이다. 공개 명단으로 대체하는 시점에도 권한 검사는 유지한다.
- 조정 명단에 반영할 차수는 디자인·개발 유형별로 선택한다. 개발 조정 기간의 디자인 변경처럼 대상 유형의 최종 공개가 끝난 경우에는 즉시 공개한다.

## 데이터 처리

즉시 반영하는 해제는 팀원 행을 삭제하고 연결 지원서를 REJECTED로 변경한다. 지원서·답변은 보존한다.
대상 유형의 랜덤 조정 기간에 ACTIVE 팀원을 해제하면 `pendingRemovalRoundId`에 랜덤 차수 ID를 기록하고 공개 명단의 ACTIVE 상태·지원서·선발 차수를 유지한다. 조정 명단에서만 제외하며, 최종 공개 트랜잭션에서 연결 지원서를 REJECTED로 변경하고 팀원 행을 삭제한 뒤 새 배정을 ACTIVE로 공개한다.
같은 팀에 다시 배정하면 해제 예약만 취소하고 기존 지원서·선발 차수를 유지한다. 다른 팀으로 이동하면 이전 팀 해제 예약과 새 팀 PENDING_PUBLICATION 배정으로 처리한다. 미공개 배정을 해제하면 해당 팀원 행을 즉시 삭제한다.
기존 상태 변경 API에서 탈퇴(WITHDRAWN)·퇴출(DISMISSED)로 변경해도 지원서를 함께 불합격 처리한다.
정상 완료(COMPLETED)는 매칭 해제가 아니므로 기존 합격 이력을 보존한다.
재배정은 현재 파트·지부·미배정 여부·TO를 다시 검증한다. 대상 유형의 랜덤 조정 기간에는 해당 랜덤 차수를 연결한 PENDING_PUBLICATION으로 저장하며, 그 외 허용 기간에는 ACTIVE로 반영한다.
본인 배정 결과 조회는 기존 개발 파트와 신규 웹·모바일 프로덕트 엔지니어 파트를 모두 포함한다.
재사용하는 비활성 팀원 행은 과거 지원서·발표 차수 연결을 끊고 운영진 수동 배정으로 기록한다. 과거 지원서와 답변은 남는다.
상태 변경 시 남아 있는 해제 예약은 취소한다. 상태 변경 API에는 이번 배정·해제의 일괄 공개 정책을 적용하지 않는다.

수동 배정, PM 합불 결정, 자동 선발, 결과 발표, 매칭 지부 이동과 프로젝트 중단은 기수별 PostgreSQL 트랜잭션 잠금을 공유한다.
프로젝트 삭제와는 기존 차수·프로젝트 행 잠금으로 조율한다. 차수가 없는 기간도 기수별 잠금으로 중복 배정을 방지한다.
자동 선발은 이미 배정된 챌린저를 다시 선발하지 않으며, 즉시 발표하는 차수에서는 해당 지원서를 불합격으로 정리한다.
PM이 새로 합격 처리할 때 같은 기수의 기존 배정과 다른 APPROVED 지원서를 검사한다. 자동 선발 대상에 동일인의 APPROVED 지원서가 여러 개 남아 있으면 선발을 중단하고 합격 내역 확인을 안내한다.
해제된 REJECTED 지원서에는 기존 불합격 지원서의 후속 차수·자동 선발 규칙이 적용된다.

`pending_removal_round_id` 컬럼·외래 키·ACTIVE 상태 제약·해제 예약 인덱스를 신규 Flyway `V2026.10.25.01.00__add_project_member_pending_removal_round.sql`로 추가한다. 기존 Flyway 파일은 변경하지 않는다.
