# 운영진 수동 배정·매칭 해제 (#1400)

## API

| 기능 | 메서드·경로 |
|---|---|
| 후보 조회 | `GET /api/v1/projects/admin/{projectId}/members/candidates?part=DESIGN` |
| 수동 배정 | `POST /api/v1/projects/admin/{projectId}/members` |
| 매칭 해제 | `DELETE /api/v1/projects/admin/{projectId}/members/{memberId}?reason=사유` |

배정 본문은 기존 팀원 추가 요청과 동일한 `memberId`, `part`를 사용한다.
후보 조회는 `keyword`, `page`, `size`를 지원하며 회원 ID 오름차순으로 반환한다.

## 권한과 검증

- 슈퍼어드민·해당 기수 총괄단은 전체 지부, 해당 기수 지부장은 담당 지부를 관리한다.
- 수동 배정 대상은 등록완료(IN_PROGRESS) 프로젝트와 해당 기수의 활동 중인 디자인·개발 챌린저다.
- 후보의 실제 파트와 매칭 지부가 요청과 일치해야 한다. 매칭 지부 이동도 반영한다.
- ACTIVE·PENDING_PUBLICATION 팀원 또는 합격 지원서가 있으면 배정 후보에서 제외한다.
- 파트 TO에서 ACTIVE·PENDING_PUBLICATION 인원을 차감한다. TO 초과 시 409로 거부하며 정원을 늘린 뒤 배정한다.
- 차수나 마감 기한은 배정·해제 조건으로 사용하지 않는다. 완료·중단 프로젝트 변경과 메인 PM 제거는 기존처럼 거부한다.

## 기존 API와 화면 연동

기존 팀원 추가·삭제·상태 변경 API도 일반 파트에 대해서는 같은 운영진 매칭 정책을 적용한다.
PM의 보조 PM(PLAN) 관리와 지원서 합격 판정은 기존 권한을 유지한다. 보조 PM 추가 시 실제 PLAN 챌린저인지 검증한다.

프로젝트 권한 응답의 `member.canCreate`, `member.canDelete`는 기존 보조 PM 관리 용도로 유지한다.
일반 팀원 수동 매칭 버튼은 새 `member.canAssign`, `member.canUnassign`을 사용한다.
각 필드는 기존 capability와 같은 `allowed`, `reasonCode`, `reason` 형식이다. 파트별 잔여 정원은 별도 정원 정보와 함께 확인한다.

## 데이터 처리

해제 시 팀원 행을 삭제하고 연결 지원서를 REJECTED로 변경한다. 지원서·답변은 보존한다.
기존 상태 변경 API에서 탈퇴(WITHDRAWN)·퇴출(DISMISSED)로 변경해도 지원서를 함께 불합격 처리한다.
정상 완료(COMPLETED)는 매칭 해제가 아니므로 기존 합격 이력을 보존한다.
재배정은 현재 파트·지부·미배정 여부·정원을 다시 검증하며, 즉시 ACTIVE로 반영한다.
본인 배정 결과 조회는 기존 개발 파트와 신규 웹·모바일 프로덕트 엔지니어 파트를 모두 포함한다.
재사용하는 비활성 팀원 행은 과거 지원서·발표 차수 연결을 끊고 운영진 수동 배정으로 기록한다. 과거 지원서와 답변은 남는다.

수동 배정, 자동 선발, 결과 발표, 매칭 지부 이동은 기수별 PostgreSQL 트랜잭션 잠금을 공유한다.
프로젝트 삭제와는 기존 차수·프로젝트 행 잠금으로 조율한다. 차수가 없는 기간도 기수별 잠금으로 중복 배정을 방지한다.
자동 선발은 이미 배정된 챌린저를 다시 선발하지 않으며, 즉시 발표하는 차수에서는 해당 지원서를 불합격으로 정리한다.
해제된 REJECTED 지원서에는 기존 불합격 지원서의 후속 차수·자동 선발 규칙이 적용된다.

스키마나 기존 Flyway 파일은 변경하지 않는다.
