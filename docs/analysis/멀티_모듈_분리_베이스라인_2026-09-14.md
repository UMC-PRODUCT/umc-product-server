## Spotless 전체 규모

**checkstyle 과 달리 spotless 는 빌드를 실패시킨다.** 그리고 `gradle/testing.gradle.kts` 가
`spotlessTest` 를 테스트의 선행 작업으로 걸어두어, 실패하면 테스트가 시작조차 하지 못한다.

`git mv` 직후 실측한 결과다.

```
:monolith:spotlessJavaCheck FAILED   ->  545개 파일
```

내용은 import 그룹 순서와 파일 끝 개행이다. `ratchetFrom("origin/develop")` 이 변경 파일만
검사하므로 그동안 가려져 있었고, 이동으로 전 파일이 새 경로가 되면서 한꺼번에 드러났다.
`spotlessApply` 로 545개가 자동 정리됐고, 와일드카드 import 1건(`NoticeVote.java`)만 수동으로 고쳤다.

즉 **"lint 폭발로 CI 차단" 은 실제 위험이었다.** 계획서의 경고가 맞았다. checkstyle 만 보고
위험이 없다고 판단하면 안 된다. 두 도구의 실패 정책이 다르다.

| 도구 | 위반 시 | 테스트 차단 |
|------|---------|-------------|
| checkstyle | warning 만 남기고 통과 | 안 함 |
| spotless | **빌드 실패** | **함** |

다음 도메인을 분리할 때도 같은 일이 반복된다. 이동 전에 `spotlessApply` 로 미리 정리할 수는 없다.
ratchet 이 이동 전에는 그 파일들을 보지 않기 때문이다. 이동 커밋과 포맷 정리 커밋을 나누는 쪽이
리뷰에 낫다.
